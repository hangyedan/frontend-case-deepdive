문제 상황

  • 20개 이상 섹션, 스크롤 연동 애니메이션 → 60fps 아닌 20–30fps

top/width는 Layout(리플로우)을 강제 유발 — Style·Layout·Paint·JS 전부 메인 스레드에서 실행되어 서로 경합.
transform/opacity는 Layout·Paint를 생략하고 Composite(브라우저의 컴포지터 스레드)로 직행하지만, 이걸 계산하는 JS 자체는 여전히 메인 스레드.

Case 1 vs Case 2 — 속성만 바꾸면 될까?

CASE 1

top/width + scroll 이벤트

card.style.top = `${40-p*40}px`;
card.style.width = `${40+p*20}%`;

JS→Style→Layout→Paint→Composite 전부 메인 스레드

CASE 2

transform/opacity + scroll 이벤트

card.style.transform =
  `translateY(${y}px) scale(${s})`;

Layout/Paint는 생략되지만 scroll→JS→getBoundingClientRect()는 Case 1과 동일하게 메인 스레드

속성만 transform으로 바꿔도 Layout/Paint 비용은 줄지만, 매 스크롤마다 JS 콜백이 도는 구조 자체는 그대로 남는다 — "절반의 개선".

animation-range

  entry 0% cover 40%;

CSS 네이티브 타임라인 — 강점과 함정

스크럽(Scrub) 제어란?

애니메이션의 진행률이 "시간"이 아니라 스크롤 위치에 직접 묶이는 방식. 동영상 편집 타임라인의 스크러버 바를 손으로 앞뒤로 끄는 것과 같다 — 스크롤을 올리면 애니메이션도 정확히 되감긴다.

setTimeout/requestAnimationFrame으로 "재생"시키는 일반 애니메이션과 달리, 유일한 입력값이 스크롤 위치라서 브라우저가 메인 스레드 개입 없이 컴포지터에서 바로 처리할 수 있다.

강점 / 약점

✓ 정밀한 스크럽 제어 (단일 요소, 1:1 매핑) — 우리 요구사항에 정확히 부합

✗ 복잡한 오케스트레이션(다중 요소 의존, pin 고정, 조건 분기)은 어려움

실무 주의사항: ① Firefox 미지원 → @supports not (animation-timeline: view()) 폴백 필요 ② 조상에 overflow: hidden이 있으면 그 요소가 스크롤 컨테이너로 잡혀 타임라인이 멈춤 (실제로 겪은 버그) ③ animation-timeline만 바꾼다고 성능이 자동 개선되지 않음 — 속성 선택은 별도 축 (→ 구역 4에서 실증)

Performance 탭 읽는 법 — 개요

녹화 버튼 → 페이지 조작 → 정지, 그 사이 브라우저가 내부적으로 한 일을 시간 순서대로 보여주는 도구.

① 상단 타임라인

CPU/NET 꺾은선 그래프 — 산 모양으로 튀는 구간이 그 순간 브라우저가 바빴다는 뜻.

Screenshots 체크박스를 켜면 필름스트립(시점별 화면 미리보기)도 같이 기록됨.

② Frames 줄

프레임 하나하나가 막대로 쌓임. 예산(60fps 기준 약 16.6ms)을 못 지킨 프레임은 빨간 표시로 드러남 — 실제 버벅임 지점.

③ 녹화 팁

같은 스크롤 길이·속도로 케이스를 비교해야 공정함. 레코딩 길이가 다르면 ms보다 비율(%) 로 비교.

Performance 탭 읽는 법 — Main 스레드

가장 중요한 줄. "메인 스레드라는 일꾼 한 명"이 시간 순서대로 무슨 일을 했는지 색깔로 보여준다.

색카테고리의미
ScriptingJS 코드 실행스크롤 이벤트 핸들러, 계산 로직 등
Rendering레이아웃 계산요소 위치·크기 다시 구하기 (리플로우)
Painting픽셀 그리기변경된 영역을 다시 래스터화
System브라우저 내부 작업GC 등 — 테스트 대상과 무관한 노이즈일 때가 많음
Messaging스레드 간 통신대체로 미미한 비중
막대가 세로로 길고 촘촘할수록 그 시간에 일이 많았다는 뜻. Case 1(top/width+JS)은 보라색(Rendering)이 유독 빽빽함 — 매 스크롤마다 레이아웃을 강제로 다시 계산하고 있다는 증거.

Performance 탭 읽는 법 — GPU · Summary

Thread pool / GPU 줄

GPU 틱은 거의 매 프레임 일정하게 찍힌다 — 화면 합성은 애니메이션 방식과 무관하게 항상 일어나는 루틴이라, 틱의 밀도만으론 케이스 간 차이가 잘 안 보인다.

transform이 절약해주는 건 "GPU를 더 굴린다"가 아니라 메인 스레드의 Layout/Paint 단계 자체를 스킵하는 것 — 그래서 진짜 비교는 GPU 줄이 아니라 Main 줄(Rendering/Painting 수치)로 해야 함.

Summary 탭

녹화 전체 구간 동안 카테고리별 누적 시간을 합산해서 보여줌 — 케이스 비교에 가장 신뢰도 높은 숫자.

Rendering이 크면 → 레이아웃 트리거 속성 의심. Scripting이 크면 → 스크롤 리스너가 매 프레임 무거운 로직을 도는 중.

실측 비교 — Chrome DevTools Performance

CaseScriptingRenderingPaintingSystem메인스레드 점유율*
1. top/width + JS433 ms446 ms320 ms410 ms10.4%
2. transform + JS390 ms294 ms221 ms353 ms7.8%
3. transform + CSS native179 ms150 ms200 ms558 ms4.3%
4. top/width + CSS native239 ms405 ms255 ms610 ms8.0%

* (Scripting+Rendering+Painting) ÷ 녹화 길이(11.2~12.2s). 레코딩 길이가 케이스마다 달라 ms 대신 비율로 비교. System은 점유율 계산에서 제외(테스트와 무관한 GC/내부 처리 노이즈 포함).

System은 오히려 CSS native 케이스(3·4)에서 더 크다 — animation-timeline: view()가 매 프레임 진행률을 동기화하는 데 드는 구조적 고정비용(스레드 간 동기화, GC 등). 하지만 Case 3은 그 손해(System +148ms, Case1 대비)보다 Scripting+Rendering+Painting에서 훨씬 크게 절약(-670ms)하기 때문에, 총 메인스레드 점유율은 여전히 4개 중 가장 낮다(4.3%).
결론: 속성 선택(transform/opacity 우선)이 먼저, 구동 방식(CSS native로 메인 스레드 비우기)이 그다음 — 두 축을 다 맞춰야 "메인 스레드 스크롤 처리" 문제가 근본적으로 해결됨. Firefox 미지원·overflow 함정은 별도 관리 필요.
